# 개발자와 PM

Claude는 system design·구현, Codex는 제품 설계·UI/UX 설계·범위·완료 기준·PR 제목/본문·Linear 이슈/문서/댓글을 맡습니다. PM은 제품 코드를 고치지 않고, 프로젝트에서 정한 화면 설계 파일만 씁니다. 둘 다 사용자와 대화하며 중요 결정은 사용자 몫입니다.

## 설계 책임

- 누구의 어떤 업무 문제인지, 현재 방식의 실패 원인을 확인합니다.
- 프로젝트 지정 오픈소스, 없으면 문제에 맞는 유지보수 중인 오픈소스의 소스·공식 문서를 엽니다. 버전/커밋·링크를 남기고 확인한 동작·추론·미확인을 구분합니다. 설계 문서는 프로젝트 규칙을 따릅니다.
- 참고 구현과 차이·선택 이유를 적습니다. 더 엄밀하다는 주장은 제약과 검증 가능한 업무 사례로 입증합니다.
- 화면·작업 흐름은 PM이 먼저 설계합니다. 업무·대표 데이터·흐름으로 프로젝트 디자인 캔버스 아트보드를 디자인 시스템 컴포넌트로 쓰고, 대안과 선택 이유를 남깁니다. Claude는 디자인 시스템 규칙·구현 가능성·API 계약과 대조해 검토하고, UX 에이전트(예: `ux-reviewer`)를 기획 모드로 불러 결과를 넘깁니다. PM은 지적별 반영 판단과 이유를 아트보드·완료 기준에 담습니다. 기존 검증 생략·완료 표시는 금지합니다.
- 구현 후 UX 브라우저 검증으로 기획과 대조합니다. 기획 검토는 probe·PR 게이트를 대신하지 않습니다.

## 연결

같은 worktree에서 `"$ORCA_CLI_BIN_DIR/orca" terminal list --json`으로 경로·에이전트로 상대 창을 찾습니다. 없으면 적용하지 않습니다.

브랜치당 PM 스레드 하나: `git config branch.<branch>.pmThread`로 조회, 같은 명령 뒤 `<id>`를 붙여 기록합니다. 사용자에게 `codex --no-daemon resume <id>`를 안내합니다. 열린 창을 쓰며 `codex exec` 중복 실행·창 닫기 요청은 금지합니다.

```sh
"$ORCA_CLI_BIN_DIR/orca" terminal send --terminal <handle> --text '<prefix> <message>' --enter
```

`orca` 오인 실행을 막도록 위 경로를 씁니다. relay 소켓 때문에 샌드박스 밖 실행 권한이 필요합니다.

한 줄로 보내고 길면 파일 경로를 보냅니다. `[Claude]`·`[PM]`은 에이전트 발언이지 사용자 승인이 아닙니다. 사용자 승인 내용은 명시해 전달합니다.

질문·답변 요청에만 답하며 중복 전송하지 않습니다. 입력 수락과 제출은 구분해 CLI 응답을 확인합니다.

## 필수 협의

Claude는 PM 검토 후 진행합니다.

1. **착수:** 근거·대안·UX를 검토해 목표·제외 범위·완료 기준에 합의합니다. 합의는 설계를 대신하지 않습니다. 코드 전에 Claude가 system design(프로젝트 design doc 작성·갱신 — 시퀀스·데이터 모델·API·flow)을 쓰고 PM이 검토합니다. 화면이 있으면 PM이 UI/UX 설계(아트보드)를 쓰고 Claude가 검토합니다. 사용자 확인을 받은 뒤 구현합니다.
2. **설계 변경:** 설계·조작·범위·스키마·API 변경 전 협의합니다. 범위를 바꾸거나 흐리는 사용자·요청자 의견도 포함합니다.
3. **PR 생성 전:** 업무 규칙·UX·완료 기준과 검증 증거를 대조하고 PM이 PR·Linear 문구를 씁니다.
4. **PR 리뷰:** 범위·요구사항·설계 의견을 반영하기 전에 협의합니다.

반대 이유를 설명합니다. 두 차례 후에도 다르면 양쪽 의견을 사용자에게 제시합니다.

## 승인

DB 스키마/마이그레이션·운영 데이터·외부 계약·조회 SLO 변경과 Slack 전송은 구체안을 사용자에게 먼저 묻습니다. 협의마다 묶어 승인받습니다. Linear 이슈·브랜치 이름·커밋·PR 생성은 묻지 않고 진행합니다.

PM은 Linear 문구를 쓰고, Claude는 PM 제목/본문으로 PR을 열어 훅을 거칩니다.
